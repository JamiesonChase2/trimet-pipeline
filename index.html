TriMet Data Pipeline.

A distributed Python and PostgreSQL pipeline for processing 15.45 million transit records.

For my data engineering course, I built a pipeline to collect historical TriMet bus data and load it into PostgreSQL. Python services running in three Google Cloud regions handled collection, processing, and backups, with Pub/Sub carrying messages between them. I then used SQL to compare arrival delays and passenger boardings.

01

Architecture

From the API to PostgreSQL

A publisher fetches data for the assigned vehicles from the course BusData API. Separate Pub/Sub topics carry GPS records and stop events to independent analysis and backup subscribers.

BreadCrumbs

Where the bus went

JSON records with position, timestamp, trip, vehicle, and odometer readings. The pipeline derives speed from consecutive observations within a trip.

StopEvents

What happened at the stop

HTML tables parsed with BeautifulSoup: arrivals, scheduled times, dwell, boardings, and alightings. Coordinates are transformed into latitude and longitude.

  1. Collect & publish

    Fetch JSON and HTML data, normalize records, and publish messages with a shared run ID.

  2. Validate & transform

    Check required fields and coordinates, normalize timestamps, and compute trip-level speed in SQL.

  3. Store & analyze

    Load relational tables, join on trip identifiers, and explore movement and passenger activity.

02

Engineering

How I handled the data

Memory

Processing GPS records in batches

To keep memory use down, I loaded GPS records into PostgreSQL staging tables in batches of 25,000. I used SQL LAG() to compare consecutive observations, check trip sequences, and calculate speed. Pub/Sub flow control limited how many messages could be waiting for processing.

Message order

Knowing when a run was complete

Pub/Sub messages could arrive out of order, including the message marking the end of a run. I added a run ID to each message and sent an expected record count at the end. Subscribers checked that count instead of treating the end message alone as proof that all records had arrived.

Data quality

Checking records before analysis

I checked for missing fields, coordinates outside the expected area, and inconsistent trip sequences. Invalid records went into JSONL logs so I could inspect them later. For stop events, I also standardized timestamps and converted State Plane coordinates to latitude and longitude.

Operations

Running collection and backups

I scheduled daily collection with cron and used systemd to keep subscribers running and restart them after failures. Separate backup subscribers saved compressed copies of the raw records, so I could inspect the original data without relying on the processed database.

What I would change

Some collection runs were missed, and backup coverage started later than it should have. I would add alerts for missed or incomplete runs, save processing progress so subscribers could resume after a crash, and account for duplicate messages in the completion checks. The run IDs and counts helped with message ordering, but they did not guarantee exactly-once processing or crash recovery.

B

Route 51 shows its largest average delay in the morning.

I compared actual and scheduled arrivals for Route 51 on weekdays, grouping the results by stop and time of day. The average of the stop-level delays was 3.61 minutes in the morning and 1.02 minutes at midday, though the midday data covered fewer stops.

How lateness was calculated

late_minutes = (arrive_time − stop_time) / 60 seconds

The query selects weekday Route 51 events with valid stop locations and excludes deviations larger than 60 minutes in either direction. It computes mean and median lateness for each stop and time period.

The displayed values are unweighted averages of those per-stop means, not averages over all passenger trips or all stop events. Midday covers fewer stops, so differences in coverage matter. The “afternoon / night” group also includes hours before 05:00.

Avoiding double-counted boardings

For each route, I selected the trip with the most boardings among trips with GPS data, then kept the top five.

Each trip has many GPS points. Joining stop events directly to those points would inflate boarding counts, so I joined on distinct GPS trip IDs instead.

Project context and data limitations

Built by Chase Jamieson for PSU's Spring 2026 CS436/536 Data Engineering course, using historical observations from an assigned subset of vehicles. Collection gaps, unequal coverage, sensor noise, and small stop-level samples limit what can be generalized. Final presentation totals and earlier notebook snapshots represent different stages of the project. This is an academic project, not an official TriMet performance report or live feed.
