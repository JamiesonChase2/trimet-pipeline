01

Architecture

Two data streams. One analytical store.

A publisher fetches data for the assigned vehicles from the course BusData API. Separate Pub/Sub topics carry GPS records and stop events to independent analysis and backup subscribers.

BreadCrumbs

Where the bus went

JSON records with position, timestamp, trip, vehicle, and odometer readings. The pipeline derives speed from consecutive observations within a trip.

StopEvents

What happened at the stop

HTML tables parsed with BeautifulSoup: arrivals, scheduled times, dwell, boardings, and alightings. Coordinates are transformed into latitude and longitude.

  1. Collect & publish

    Fetch JSON and HTML data, normalize records, and publish messages with a shared run ID.

  2. Validate & transform

    Check required fields and coordinates, normalize timestamps, and compute trip-level speed in SQL.

  3. Store & analyze

    Load relational tables, join on trip identifiers, and explore movement and passenger activity.

02

Engineering decisions

Designing for scale, data quality, and operations

Memory

Bounded-memory processing with PostgreSQL staging

I buffered GPS records in batches of 25,000 and inserted them into PostgreSQL staging tables. SQL LAG() window functions handled trip ordering, sequence checks, and speed calculations. Pub/Sub flow control limited outstanding messages.

Message order

Handling out-of-order messages

I attached run IDs to messages and published an expected-record count after each run's data had been sent. Subscribers used that count to continue processing when the completion sentinel arrived before the remaining records.

Data quality

Validation and invalid-record logging

I implemented checks for required fields, geographic bounds, and trip sequence consistency, with invalid records written to JSONL logs for investigation. Stop-event transformations normalized timestamps and converted State Plane coordinates to latitude and longitude.

Operations

Scheduled execution and independent backups

I configured cron for daily publishing and systemd to manage subscriber processes and restart them after failures. Separate backup consumers compressed raw records for inspection independently of the transformed database.

Reliability improvements

My next priorities are durable checkpoints, duplicate-aware completion checks, and alerts for missed or incomplete runs. Collection gaps also highlighted the importance of establishing backup coverage early. Run IDs and record counts address message ordering, but do not by themselves guarantee exactly-once processing or recovery after a crash.

How lateness was calculated

late_minutes = (arrive_time − stop_time) / 60 seconds

The query selects weekday Route 51 events with valid stop locations and excludes deviations larger than 60 minutes in either direction. It computes mean and median lateness for each stop and time period.

The displayed values are unweighted averages of those per-stop means, not averages over all passenger trips or all stop events. Midday covers fewer stops, so differences in coverage matter. The “afternoon / night” group also includes hours before 05:00.

A join that preserves the right grain

I selected the highest-boarding trip for each route among trips with GPS data, then kept the top five routes by that trip-level count.

The query joins stop events to distinct GPS trip IDs. This avoids multiplying passenger counts by the number of GPS points per trip.

Project context and data limitations

Built by Chase Jamieson for PSU's Spring 2026 CS436/536 Data Engineering course, using historical observations from an assigned subset of vehicles. Collection gaps, unequal coverage, sensor noise, and small stop-level samples limit what can be generalized. Final presentation totals and earlier notebook snapshots represent different stages of the project. This is an academic project, not an official TriMet performance report or live feed.
